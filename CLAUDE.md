# CLAUDE.md — larabill

Entry point for Claude Code in this package. It inherits from the umbrella `~/development/packages/aichadigital/CLAUDE.md` (do not duplicate the rules on the dependency bot, Packagist webhooks, branch protection or lessons learned — they live there).

## What this package is

Larabill is the **billing core** of the Larafactu ecosystem (AichaDigital):

- Immutable invoices with UUID v7 (char 36 string, not binary — ADR-006 consolidates the standard)
- Tax calculation (Spain, EU, worldwide); intra-community VAT/NIF verification is owned by `lararoi` — larabill consumes it through an optional thin bridge (`Actions\VerifyVatNumber`, delegates to `VatVerificationServiceInterface`), NOT coupled to emission (reverse-charge is decided by `is_roi_taxed`) (AID-309)
- Temporal fiscal data (issuer `CompanyFiscalConfig` + recipient `UserTaxProfile`)
- Pricing by frequency (`Article` + `ArticlePrice`, ADR-004)
- VeriFACTU compliance (via `lara-verifactu`)

**Stack:** PHP 8.4+ (`^8.4`), Laravel 13 (`^13.0`) since the 9.0 line (AID-1778: the platform check rejects php83; 8.x stays on security support — see README «Version support» and AID-1793), Pest. Framework-agnostic (no coupling to Filament). License AGPL-3.0-or-later.

## Inviolable rules (summary — detail in CRITICAL_RULES.md)

- **Migrations:** every package table has a `.php` (timestamped, auto-loaded in dev) **AND** a `.php.stub` (published by `larabill:install`). Only 2 stubs are consumer-only (they modify the consumer's `users`): `add_user_relationships_to_users_table.php.stub` and `rename_user_id_to_owner_user_id_in_user_tax_profiles.php.stub`.
- **The `.php.stub` is an artifact derived from the `.php` (ADR-007):** byte-identical, regenerated with `bin/sync-migration-stubs`. NEVER edit a `.stub` by hand — edit the `.php`, run the script, commit both. The byte-identity guardrail uses `LARABILL_KNOWN_SCHEMA_DIVERGENCES`, which must stay EMPTY.
- **`$migrationOrder`** in `LarabillInstallCommand` must match the real stubs 1:1 (32 entries today). A consistency test (`tests/Unit/Console/MigrationOrderConsistencyTest.php`) validates 1:1 + `.php`↔`.stub` byte-identity in CI. A green build does NOT prove the contract: the install command's fallback to the timestamped `.php` makes a missing stub *appear* to work — that is how the broken contract of v0.8.2 slipped through.
- **FK to users:** ALWAYS `MigrationHelper::userIdColumn($table, 'col')`. Never `$table->foreignId()` directly. It emits UUID v7 char(36) exclusively (ADR-006); `int`/`ulid`/`larabill.user_id_type` removed in v0.8.0.
- **Money:** ALWAYS a base-100 integer (`12,34 € → 1234`) with the `FixedDecimalCast:2` cast from `lara100` (value object `FixedDecimal`, AID-237). NEVER float/decimal. The column stays `integer`; the cast materialises the value object.
- **Fiscal numbering: ALWAYS `InvoiceNumberingService::generateNumber()`** (single owner, AID-390). `fiscal_number`, `prefix`, `series_number` and `fiscal_year` come from the SAME `InvoiceNumber`. The counter's scope is the ISSUER (null → sentinel `GLOBAL_SCOPE`), never the billed customer (`billable_user_id`, ADR-003). The **series** (`prefix`) passed to it is ALWAYS resolved with `InvoiceSeriesResolver` (AID-307), never hardcoded `'FAC'`/`'PRO'`; the `serie` (int) is the fiscal TYPE, distinct from the series.
- **The fiscal series is decided by the CONSUMER — the package has no default (AID-589, v6.9.0).** `config/larabill.php` publishes `series.*`, `invoice_prefix` and `proforma_prefix` as `null`: with no per-call series, no config and no legacy key, `InvoiceSeriesResolver::resolve()` throws `MissingFiscalSeriesException` (`@api`) instead of falling back to `defaultPrefix()`. `InvoiceSerieType::defaultPrefix()` still exists and is still `@api`, but the resolver **does not consult it**. Every harness or consumer declares the series explicitly.
- **Article prices: at most ONE active per `(article, frequency)` on any date** (AID-601, ADR-012). The overlap condition has a single source (`ArticlePrice::scopeOverlapping()`); the `saving` hook is the safety net and **`ArticlePriceService::setPrice()` is the guarantee** — use it whenever concurrency matters (it locks the parent `articles` row, not the prices: `FOR UPDATE` does not serialise an insert that matches zero rows). Pre-existing data: `larabill:diagnose-price-overlaps`.
- **The recurring price comes from the CONTRACT, not the catalogue (AID-956, ADR-013).** `ArticleServiceStatus.effective_price` is **contractual state**, not a cache: `RecurringBillingService` bills it via `PricingService::createPricingDetailsForContract()` and does not consult `ArticlePrice` or `ArticleOverride` to decide the amount. Changing the catalogue or an override does **not** reprice live agreements (only the amount: `shouldGenerateInvoice()` still reads `billing_days_in_advance`, so the catalogue still decides WHEN it is issued). `updateEffectivePrice()` is an explicit consumer act and the engine **never** calls it. No contractual price → `MissingContractPriceException`; **zero is a valid price** and is billed at zero («absent» is `null`, and only `null`).
- **When an active tax profile is created, EVERY user of ANY closed profile of the owner is relinked** (AID-1301, v6.14.0). `UserTaxProfile::updateLinkedUsersToNewProfile()` first reads the ids of the closed profiles (`valid_until` not null, not soft-deleted) and runs **a single bulk `UPDATE`** on the configured user model: no user events and no subquery on `user_tax_profiles` inside the `UPDATE`, because users and tax profiles may live on different connections. If the owner has no closed profile, **the users table is not queried** (so an installation without `current_tax_profile_id` can create the first profile). The owner's first link is NOT done here (AID-967). Declared ceiling: one bound parameter per closed profile of the owner. `createForOwner()` is not atomic (close, insert and relink are three writes).
- **Issued invoices are immutable.** Do not edit anything with status ≠ `draft`.
- **Agnostic tests:** use `config('larabill.user_model')` for type assertions, do not hardcode `User::class`.

## Note on suite memory (AID-976)

`phpunit.xml.dist` declares `memory_limit = 1G` in a `<php>` block. **Do not remove it**: the suite does not fit in PHP's default 128M and dies in two different places depending on the mode — under `--parallel` a worker blows up rendering a PDF (dompdf), sequentially the arch test falls inside `nikic/php-parser`. In parallel it shows up as an intermittent flake (~50%) because the split across workers varies with the seed, and what it prints is **paratest's help page**, which is what paratest does when a worker dies: it looks like an invalid option and it is not.

It lives in the XML and not in a composer script because paratest launches each worker as its own PHP process: the worker reads that file, but never the parent's inline flags (measured: `-d memory_limit=512M` lowered the frequency without removing it).

## Note on local PHP 8.4

Historical: a "table already exists" bug with in-memory SQLite on local PHP 8.4 was documented. **It did NOT reproduce on 2026-10-26 with PHP 8.4.27** (full suite green, AID-1778 T5d). Since the 9.0 line the runner is `php84` — the platform check in `composer.json` rejects php83, so the whole suite, phpstan and pint run with `php84` (`PHP84="$HOME/Library/Application Support/Herd/bin/php84"`). The history is kept in case it reappears on another machine.

## Frequent anti-patterns

- Creating a `.php.stub` without its `.php` → it is not auto-loaded in tests/dev
- Adding a `$migrationOrder` entry without the matching stub → install fails
- Using Spatie's `hasMigration()` → requires a manual `vendor:publish`, breaks the install command flow
- Assuming `Auth::user()->id` is an int → larabill is UUID-first (ADR-006); breaking that assumption in helpers, DTOs, casts or tests
- Reintroducing `larabill.user_id_type`, `LARABILL_USER_ID_TYPE`, `int`/`ulid` support, or the CLI flag `--user-id-type=` → removed in v0.8.0 (ADR-006). Reopened only with a concrete client case (see ADR-006 §"Criterios de reapertura").
- Reintroducing `Customer`/`CustomerFiscalData` → deprecated since ADR-003 (use `User` with `parent_user_id` + `UserTaxProfile`)
- Reintroducing binary UUID → discarded; the standard is UUID v7 char(36) (ADR-006). Historical incompatibility with Filament, a dependency already removed from the package.
- A migration that transforms data WITHOUT a test of its upgrade path → since AID-398 the upgrade promise IS assumed (stable version = respect for data): seed the legacy state → run the migration → verify (pattern: the AID-390 backfill test). The historical rule «dev-main does not promise upgrades» became obsolete with 1.0.
- Reintroducing a numbering generator of its own in a service (`rand()`, cache counter, MAX+1) → fiscal numbering has a single owner, `InvoiceNumberingService` (AID-390); always delegate
- Confusing the fiscal TYPE (`serie`/`InvoiceSerieType`) with the real SERIES (`prefix`) → since AID-307 (v5.0.0) they are different things: the type goes to AEAT as `TipoFactura`, the series (`prefix`) as `NumSerieFactura`. Never hardcode `'FAC'`/`'PRO'` (use `InvoiceSeriesResolver`), never send `$invoice->serie->value` as the series to Verifactu, never go back to the `invoices` unique without `prefix`.
- Seeding `invoice_series_control` with `user_id => null` in fixtures → the global scope is the sentinel `InvoiceSeriesControl::GLOBAL_SCOPE`; NULL was retired (it does not collide in a unique)
- Assuming `composer test` (SQLite suite) proves the real contract → SQLite does not preserve composite indexes or real char(36) lengths. The contract is proved in `tests/Integration/Mysql/` against a real engine within the operator's freeze: MySQL 8.4 and MariaDB 11.4 (CI and local; local instance map in `.claude/CRITICAL_RULES.md` §A). NOT MySQL 9.x nor MariaDB 11.8/12.x, even though they are LTS (AID-1319).
- Hardcoding `'user_id' => 1` (or any int) in test fixtures → use the constants `TestCase::USER_UUID_1/2/3`.
- Reintroducing surface removed in v6.0.0 (AID-423) → `BillingService` (use `InvoiceService`), the `user_id` shims of `UserTaxProfile` (`user()`, `user_id`, `getActiveForUser`, `getValidForUserAt`, `createForUser`, scope `forUser` → the `owner*` surface), the `HasUserRelationships` aliases (`taxProfiles`, `activeTaxProfile`, `withActiveTaxProfile`). In `UserTaxProfile` fixtures the column is `owner_user_id` (factories are unguarded: a `'user_id'` goes straight to a non-existent column).
- Proposing a breaking change without a qualified and documented usage imperative → contradicts `STABILITY.md` (in force since v6.0.0); majors are not spent on aesthetic taste.
- Querying `invoice_templates`/`CompanyTemplateSettings` with the series label (`getInvoiceType()`) or hardcoding template types → since v6.6.0 (ADR-011) the registry vocabulary is `TemplateInvoiceType::registryKey()` and the single derivation is `DomPDFService::resolveTemplateType()`; the series label lives only in `pdfFilename()`.
- Disabling `larabill.pdf.validate_fiscal_content` to «fix» a red render test → the red means the template drops mandatory fiscal content (ADR-011); fix the template, never the guard. The config escape is for installations that consciously take the risk, not for the suite.
- Seeding two overlapping ACTIVE prices of the same `(article, frequency)` → since AID-601 the package rejects it (`OverlappingArticlePriceException`); in fixtures, use disjoint ranges, different frequencies or different articles. And writing prices bypassing `ArticlePriceService` where there is real concurrency: the `saving` hook is a safety net, not a guarantee (measured: without the lock, 5-6 of 6 concurrent processes write).
- Fixing the index comment of `create_article_prices_table` so it stops promising what it does not deliver → the migration is published and in the manifest with its `sha256` (D6 of ADR-012). `MigrationOrderConsistencyTest` gives a **false green** on that change (it compares `.php` with `.php.stub`); the one that goes red is `ShippedMigrationImmutabilityTest`.
- Seeding a temporal fixture with a FUTURE date against a read that filters by validity (`activePrices()` requires `valid_from <= now()`) → the row is correctly excluded and the test fails against correct code. Fixture dates are RELATIVE (`now()->subMonth()`), never literals that may fall in the future. Diagnostic corollary (AID-601): a red whose observed value does not fit the hypothesis (you expected failure A and see value B) is investigated in the FIXTURE before the code — the written plan may bring the fixture wrong.
- Restoring with `git checkout <file>` after breaking something on purpose to prove a test's sensitivity → if the fix is NOT committed yet, `checkout` restores HEAD and **erases your work**. Save the state first (a prior commit, or a copy) and restore to it.
- Treating as verified a change that REMOVES a default of business value (from code or from `config/larabill.php`) because the SQLite suite is green → the four gated harnesses (`tests/Concurrency` + `Integration/{Mysql,InstallMysql,UpgradePath}`) hang from `MysqlIntegrationTestCase`, which **DOES receive `config/larabill.php`** (the ServiceProvider calls `->hasConfigFile()` → `mergeConfigFrom`), but declares fewer consumer values than the SQLite `TestCase`. When a business default becomes `null`, the harness sees `null` and its emission paths fail loud; SQLite stays green because it does not exercise those paths. It has broken CI twice (AID-553 `user_model`, AID-589 fiscal series). Run them locally BEFORE pushing; command in `.claude/CRITICAL_RULES.md` (section A). The fix is to declare the value in the harness, NEVER to resurrect the default. A mechanical guardrail was evaluated and discarded (AID-647, Canceled): CI already runs `tests/Concurrency` unconditionally on every MR and blocked both recurrences — the real cost is a re-push, not a downstream bug.
- Reintroducing a fiscal series literal in `config/larabill.php` (`'FAC'`, `'PRO'`, `'TIK'`, `'RECT'` as the `env()` default) → v6.9.0 publishes them as `null` on purpose (AID-589); a test reads the file with `require` and fails if they come back. The series is the consumer's decision, not the package's.
- Making recurring emission resolve the price from `ArticlePrice`/`ArticleOverride`, or calling `updateEffectivePrice()` from the engine → since AID-956 (ADR-013) the amount comes from `effective_price` and revision is a consumer act; refreshing it at emission would overwrite imported prices right before billing them. And `PricingService::createPricingDetailsForService()` is **not** the emission path: it is a quote at the current catalogue, deliberately untouched (`createPricingDetailsForContract()` is the emission one).
- Writing `if (! $price)` on a contractual price → confuses **zero** (a valid agreement, billed at zero) with **absent** (`null`, which throws `MissingContractPriceException`). There is a test that pins the zero case precisely to prevent it.
- Going back to choosing ONE «previous profile» in the `UserTaxProfile` hook (`orderBy('valid_until')->first()` or any tie-break) → `valid_until` is a `date` and is stamped with the **successor's** `valid_from` minus one day: two creations taking effect on the same date close their predecessors with the same value and the engine picks one (AID-1301). Nor put the list of closed profiles as a subquery inside the users `UPDATE`, nor swap the bulk `update()` for a loop of `save()`/`saveQuietly()`: the `UserTaxProfileRelinkTest` tests turn them red on purpose.
- Narrowing a view name with the `View::exists()` facade to please larastan → the assertion `@phpstan-assert-if-true view-string` lives on the `Illuminate\Contracts\View\Factory` contract, not on the facade; with the facade PHPStan stays red (AID-1305). Use the contract resolved from the container, never `@phpstan-ignore`, baseline or cast.
- Reading as a regression of the candidate a consumer architecture red in the conformance gate with a symlinked `path` repository → tests that separate own code from `vendor` by path (`str_starts_with($file, base_path('vendor'))`) classify the package as own code because the symlink resolves outside `vendor/`. Repeat with `symlink: false` and verify identity by checksum (measured in the v6.14.0 gate: 2 false reds that disappear with the copy).
- Giving a RANDOM default (`faker->boolean(N)`, `optional()`, `randomElement`) to a factory field that governs a guard, policy, visibility or resolution (`is_immutable`, `is_roi_taxed`, `is_exempt_vat`, state flags) → it is a latent flake (AID-508/AID-558/AID-581): the day the guard appears, ~N% of the fixtures that do not declare it flake. The default is deterministic (`false`/typical value); the test that needs the case declares it. Facing a factory coin-flip flake, the fix is to DE-RANDOMISE the default, not to pin the affected fixture (that leaves the other coins alive).

- **Stability contract `STABILITY.md`** (in the dist, since v6.0.0): breaking only with a qualified and documented usage imperative; every major auto-upgradeable from the previous one (AID-398); a deprecation stays alive ≥1 full major before removal; every major requires a record in `approvals/majors/`. A feature/fix that breaks surface without a documented real case **contradicts the contract** — stop and confront it with `STABILITY.md`. Deferred by design: **AID-560** (target series in the conversion; the mechanism already exists in the `series` option of v6.7.0).
- **"Nothing decimal in the DB" debt: CLOSED** (AID-240/242/246 — AID-286 documents the closure). Zero `decimal`/`float` columns in migrations; every money/rate model uses `FixedDecimalCast:2`. Sole survivor with an `integer` cast **by deliberate decision**: `tax_rates.rate` (tax core via `VatCalculationStrategy`, base-100 of the %, `/10000` → fraction; highest risk, out of scope barring a concrete case).
- **Legal retention contract (AID-221):** `Invoice` and `UserTaxProfile` implement `AichaDigital\LaraPrivacyCore\Contracts\LegallyRetainable` (single method `retainedUntil(): ?DateTimeInterface`). The contract is **owned by the core** (`lara-privacy-core`); larabill is an adapter. The `isUnderRetention` gate is resolved by the core's `CheckLegalHold` — **without** `RetentionBasis`/`legalHold()`/`isUnderRetention()` on the models. `Invoice`: fiscal → end of the fiscal year of `invoice_date` + `larabill.retention.fiscal_years` (env `LARABILL_RETENTION_FISCAL_YEARS`, default 6); PROFORMA/no date → null. `UserTaxProfile`: MAX over its invoices (computed even when soft-deleted; orphan → null). Compute, do not materialise.
