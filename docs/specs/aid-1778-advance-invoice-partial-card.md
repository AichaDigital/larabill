## 3. S6 — `register()` accepts `PARTIALLY_PAID`, allocating exactly each invoice's `amountOutstanding()`

### 3.1 The status list (one widening, both checks agree)

- `Ledger::legacyPayableStatuses()` (`src/Services/Payments/Ledger.php:148-151`) is extended with `InvoiceStatus::PARTIALLY_PAID`. Because `assertEligible()` reads the list (`GroupedPaymentService.php:158`) and `process()` under Legacy reads the same list through `payableStatusesFor()` (`PaymentService.php:141-142` → `Ledger.php:158-161`), the pre-`process()` eligibility check and the under-lock check agree by construction — the wishlist's requirement. The docblocks of both lists (`Ledger.php:70-83`, `:140-146`) are rewritten: Legacy no longer means «whole invoices only».
- No other status joins the list. `PAID`, `DRAFT`, `CANCELLED`, `CONVERTED`, `CONVERTING` stay non-payable; `Ledger::payableStatuses()` (`Ledger.php:136-139`) is untouched.

### 3.2 The `alreadyActivelyPaid` guard must be re-scoped (discovered interaction)

- A `PARTIALLY_PAID` invoice has, by definition, at least one ACTIVE allocation row (`recomputeCollectionState()`, `Invoice.php:815+`: `0 < paid < total` requires active allocations). The guard at `GroupedPaymentService.php:162-164` refuses exactly those invoices via the `active_invoice_id` pivot read (`:129-138`) — widening the status list alone would make S6 dead on arrival.
- **Change:** the guard fires only when the invoice's collection status is NOT `PARTIALLY_PAID`. Rationale: the guard's fiscal intent («one card charge per invoice, never a second full settlement») is preserved by the widened machinery itself — a card payment that settles the outstanding moves the invoice to `PAID`, and a second `register()` is then refused by the status list.
- **Behavior preservation proof for the 8.3 statuses:** today the guard is unreachable for any invoice whose status ∈ {SENT, OVERDUE, PENDING} **except** the stale-stamp case (a consumer hand-stamping SENT over allocations). In that case the invoice is not `PARTIALLY_PAID`, so the re-scoped guard still fires — the observable 8.3.0 behavior is identical. Differential test in §8 pins it.

### 3.3 Sum and allocations become outstanding-based

- `assertEligible()`: the accumulated sum at `GroupedPaymentService.php:166` becomes `Σ $invoice->amountOutstanding()`. The mismatch at `:169-171` keeps `GroupedPaymentValidationException::amountMismatch` — **the same exception type a total mismatch raises today**, so the consumer's existing `payment_mismatch` handling catches it. `amountOutstanding()` is a fresh query per invoice (`Invoice.php:754-773`); this runs inside `register()`'s transaction with the invoice rows locked (`:69-73`), so the sums are under-lock reads. Keeping one query per invoice is accepted (batching the pivot SUM like `:127-138` is an optional refactor, not required).
- `legacyRequest()`: the allocation amount at `:189` becomes `$invoice->amountOutstanding()` (read under the same lock). The `notPayableAmount` floor at `:186-187` stays on `total_amount`, unchanged. A zero outstanding cannot reach `Allocation` (positive-by-invariant, `src/ValueObjects/Allocation.php:21-29`): under §3.2 an invoice whose allocations cover it fully is either `PAID` (status-refused) or stale-stamped (guard-refused).
- Under-lock agreement in `process()`: each allocation is checked with `assertWithinOutstanding()` against the freshly locked instance. When the allocation equals the outstanding read under the lock, it passes at the boundary.

### 3.4 The Legacy race, restated (docblock + CHANGELOG obligation)

- Today (`PaymentService.php:114-119`, `GroupedPaymentService.php:41`): a `receive()` committing between `register()`'s transaction and `process()`'s transaction surfaces as `notPayableStatus`. After the widening, a race on a formerly-whole invoice has TWO cases (J3, round 3), decided by the under-lock check order — `Ledger::assertPayable(...)` runs BEFORE `assertWithinOutstanding(...)` (`PaymentService.php:147-151`):
  - **Partial concurrent payment:** the invoice stays `PARTIALLY_PAID` and the fresh outstanding is smaller than the allocation built in the earlier transaction → **`AllocationExceedsInvoiceException`**. This — and only this — is the declared change of the race's failure mode: the caller-amount mismatch (§3.3) is still `amountMismatch`; only the between-transactions PARTIAL race changes exception type.
  - **Fully-settling concurrent payment:** the invoice is `PAID` and the STATUS check fires first → **`notPayableStatus`**, byte-for-byte today's mode. No new failure mode is invented for the full case; R4 pins both.
- No consumer-visible mitigation is added: the race remains fail-safe (the second transaction writes nothing before the checks; `process()` validates before `GroupedPayment::create()` at `:154-162`).

### 3.5 Replay is byte-for-byte unchanged for invoices that are not partially paid — proof

- `amountPaid()` sums ACTIVE allocations only (`Invoice.php:754-762`); an invoice accepted by the 8.3 list (SENT/OVERDUE/PENDING, not in the active-pivot set or guard-refused) has zero ACTIVE allocations, so `amountOutstanding() === total_amount` exactly. The allocations built in `legacyRequest()` and the `amount` passed to `deriveIdempotencyKey()` (`GroupedPaymentService.php:199-205`) are therefore identical to 8.3.0 for every invoice the old code accepted → identical derived keys.
- `replayMatches()` under Legacy (`PaymentService.php:225-249`: payer, currency, amount, distinct direct-allocation ids) is not modified at all; `forLegacyReplay()` (`ReceiveRequest.php:96-115`) is not modified. The pre-check replay path in `register()` (`:58-67`) is not modified.
- **Replay when the outstanding changed between attempts:** the replay path never reads invoices or outstandings — it compares immutable payload fields and returns `$existing->load('invoices')` (`GroupedPaymentService.php:65`). A replayed key with the same payload returns the original payment verbatim whatever happened to the invoices since (a manual partial payment landing between attempts does not invalidate the replay and does not move new money). The `ReplayPolicy::Legacy` race note is rewritten to cover both: a stale snapshot between the two transactions can now also surface as `AllocationExceedsInvoiceException` (§3.4 — the PARTIAL race only; a fully-settling race keeps the status refusal, J3), while a same-key replay is unaffected by outstanding drift. Both docblocks and the CHANGELOG `Changed` entry say so.

### 4.1 Signature (option A, settled 2026-10-25; no regime resolution from the profile)

- New class `src/Services/AdvanceInvoiceBuilder.php`, `@api`, with ONE public method:

public function forCreditEntry(
    CreditMovement $entry,

- The consumer passes the series (`MissingFiscalSeriesException` rule of 6.9.0 applies — no default series exists, `config/larabill.php` ships `null`; the resolver at `src/Services/InvoiceSeriesResolver.php` fails loud), the description, `tax_group_id` and `is_roi_taxed`, exactly like an ordinary emission. **Resolving the VAT regime from the consumer's tax profile inside larabill is explicitly out of 8.4** (S2 settled; it would be a new domain with its own ADR). `is_exempt_vat` takes no part, as everywhere else (`TaxCalculationService.php:86-110`).
- `gross` is `$entry->amount` (base-100, `FixedDecimal` scale 2); the customer is `$entry->billable_user_id`; the currency is `$entry->currency`. Money in every new signature is `FixedDecimal`; no floats (S1).

### 4.2 Validation of the entry

- **Entry kind:** `$entry->isEntry()` must hold (`CreditMovement.php:117-123`); an exit → `InvalidCreditMovementException::notAnEntry` (existing, `src/Exceptions/InvalidCreditMovementException.php:16-19`). Both `SURPLUS` and `TOP_UP` are accepted — both are money collected (S1 «from a gross amount collected»); restricting to `SURPLUS` would leave `TOP_UP` advances unbuildable for no fiscal reason.
- **Active:** `$entry->isReversed()` must be false (`CreditMovement.php:125-127`); a reversed entry → new named constructor `InvalidCreditMovementException::reversed(string $movementId)` (additive on an `@api` class).
- **No advance linked yet:** `$entry->advance_invoice_id !== null` → `CreditMovementAlreadyLinkedException::forMovement` (existing, `src/Exceptions/CreditMovementAlreadyLinkedException.php:14-20`), the same refusal `linkAdvanceInvoice()` enforces later (`CreditMovement.php:189-208`). The builder does NOT link; the consumer links after its own issuance (wishlist flow). **The builder is deliberately not idempotent (O5, operator decision L7):** a double call mints two drafts and BOTH are valid artifacts — «mismo importe» does not prove the same attempt, so no reuse rule is adopted; the cleanup of orphan drafts is the consumer's, documented in 8.4. What the one-to-one link prevents (§5.6) is the second draft ever being ISSUED as an advance of the same entry: the first `linkAdvanceInvoice()` succeeds, the competing one fails loud. A test pins both results (§8.2 R10b).
- **Currency (D3 parity):** when `CompanyFiscalConfig::getActive()->currency` is non-null and differs from `$entry->currency`, refuse with a new named constructor `GroupedPaymentValidationException::creditCurrencyMismatch(string $movementId, string $entryCurrency, string $configCurrency)` (additive; mirrors `currencyMismatch`'s semantics for the credit-ledger side).

### 4.3 Reverse base and the cent (larabill's rounding rule, documented)

- Effective rate: the group's rates summed, `R = Σ rate_i / 10000` (each `rate_i` is base-100 percent, `TaxRate.php:20-21`; forward computation taxes the same base with every rate, `VatCalculationStrategy.php:27-40`, so the reverse divisor is `1 + Σ rates`).
- **Reverse rule:** `base = HalfUp(gross / (1 + R))` computed on exact `Brick\Math\BigDecimal` arithmetic — the AID-1527 §3-bis discipline, precedent `frozenRateTaxAmount()` (`SettlementService.php:590-598`) — and `tax = gross − base` as an exact residual, never an independent rounding. This makes `base + tax === gross` hold by construction and `total_amount === $entry->amount` to the cent (S3).
- **The reverse-inclusive cent is SETTLED against the forward rule (J6, not reopened):** on the wishlist's pinned case the reverse rule gives `base = HalfUp(10000/1.21) = 8264`, `tax = 10000 − 8264 = 1736`; the FORWARD calculation on the SAME base gives one cent less — `8264 × 21 % = 1735,44 → HalfUp 1735`. Both directions cannot hold at once; the wishlist pins the reverse-inclusive pair (S3: «100,00 € at 21 % → 82,64 + 17,36»), so the advance is built reverse-from-gross and the residual identity `tax = gross − base` is the rule — the forward figure on the same base is a different operation this spec does not adopt, and the one-cent difference is its accepted consequence. T6 additionally measures AEAT acceptance of that advance F1 (§6).
- **Multi-rate tax groups: REFUSED, loud.** A group carrying more than one rate → `InvalidAdvanceInvoiceException::multiRateTaxGroup(TaxGroup $group)` (new `@api` exception, §7). Justification: the house doctrine is to never invent a per-rate distribution (explicit amount on a multi-rate original → `UnresolvableRectificationRateException`, `SettlementService.php:541`; ambiguous credit article → `UnsettleableInvoiceException::ambiguousCreditArticle`), and the deduction pro-rata of §5 keys off the advance's frozen per-rate breakdown — a single-rate group keeps both ends exact. A multi-rate advance could be supported later by allocating the reverse base across rates (largest-remainder), which is a minor extension, not a design change.
- **Missing/unresolvable group (G3/G8 — O1 resolved):** `taxGroupId = null` or an id that does not resolve → the line carries no tax: `tax = 0`, `base = gross`, and `taxes_applied: []` — exactly the null-group branch of `TaxCalculationService::calculateForInvoiceItem()` (`TaxCalculationService.php:103-115`: `$taxesApplied = []`, `totalTaxAmount = 0`). Per G8 this representation is pinned SEPARATELY from an explicit zero-rate group (next bullet) and the docs distinguish them: an absent group and a zero-rate group are different fiscal statements.
- **Explicit zero-rate group (G3):** `tax = 0`, `base = gross`, and `taxes_applied` carries the strategy's OWN emission — ONE entry `['source_rate_id' => …, 'name' => …, 'rate' => 0, 'amount' => 0]`, because `VatCalculationStrategy::calculate()` emits one entry per rate of the group (`VatCalculationStrategy.php:34-43`) and a zero rate is a real entry, not an absent one. The frozen path persists it verbatim. A test pins the two representations apart (§8.2 R7).
- **`is_roi_taxed = true` with a group carrying real tax** (Σ rates > 0): the builder refuses EARLY, before any write, with a new named constructor `ReverseChargeWithTaxException::forTaxGroup(TaxGroup $group, int $rateSum)` (additive on the existing `@api` class) — never a silent zero (S2). The AID-929 guard inside `createInvoiceRow()` (`InvoiceService.php:971-973`) remains as the second net; the builder's early refusal fails before the draft transaction even opens.

### 4.4 The draft (never issued, one line, no article, frozen amounts)

- The builder calls `InvoiceService::createInvoice()` with `'type' => 'invoice'` (fiscal INVOICE serie), `'series' => $series`, `'status' => 'draft'` — the explicit-status contract skips phase 2 (`InvoiceService.php:286-291`), returning an unnumbered DRAFT with the five number/issuance fields NULL (ADR-016 §7.1). The builder NEVER issues; issuance is the consumer's act through `InvoiceService::issue()` (`@api`, ADR-016 §11.1). The wishlist's `InvoiceIssuanceService` is a clientes-side name; larabill's primitive is `issue()`.
- ONE line, no `article_id`, built on the **frozen path** (frozen keys present → persisted verbatim, `InvoiceService.php:1102-1136`; same precedent as the proforma clone and `AdvanceDeductionLineTest`): `quantity: 100`, `base_price: base` (unscaled), `description: $description`, `taxable_amount: base`, `total_tax_amount: tax`, `taxes_applied: [['source_rate_id' => …, 'name' => …, 'rate' => rate_i, 'amount' => tax]]` (the exact shape `VatCalculationStrategy` emits, `VatCalculationStrategy.php:34-43`; a null group carries `[]` and an explicit zero-rate group carries its single zero entry — the G3 distinction of §4.3), `total_amount: gross`, no `deducts_invoice_id`. Freezing guarantees the emitted document can never re-derive against a live catalog that changed between build and issue.
- Invoice totals are the item sums (`InvoiceService.php:959-962`): `taxable = base`, `total_tax = tax`, `total = gross`. `is_roi_taxed` travels in the invoice data (`:947-949`). No tax profile → `user_tax_profile_id = null` and the snapshot resolves from the billable user (`InvoiceService.php:897-908`, `:1005-1030`) — the builder does NOT mirror `MissingUserTaxProfileException`, which belongs to unattended recurring emission (`RecurringBillingService.php:402-413`); the builder is a consumer-invoked primitive (S1) and the consumer's own issuance owns coherence at `issue()`.
- The draft's collection axis stays DRAFT; stamping, issuance and Verifactu registration are the consumer's flow (S1: the package never issues on its own, DECISION 4 of the 8.3.0 handoff stands).
- **The documented consumer sequence is build → link → issue (operator decision L9):** the consumer builds the draft (§4), links it to the entry (`linkAdvanceInvoice()` — which validates the entry, the advance's exclusivity and the advance's DRAFT status, §5.6), and only then issues it. If issuance fails, the recovery retries issuing the SAME linked draft — never builds another one for the entry (§5.6).

## 5. S4 — the positional pro-rata helper serving both exits (revision 3 — operator decisions L6/L8)

Round 1 judged S4 cosmetic (§10 G1/G2): the last-exit test keyed on `remaining()` at call time and the fiscal reads ran outside the payment locks. Operator decision L6 keeps option A (positional, larabill-owned) and imposes two conditions the text must FIX: (1) an explicit total order of the exits of an entry — the position comes from that order, never from the live balance or an undefined «previous exits» set; (2) a reversal rule — later exits keep or lose their split must be decided, never assumed away by excluding the reversed exit from the balance. Revision 2 satisfied both with a schema-free reconstruction; revision 3 satisfies them MORE strongly on operator decision L8 — the position is PERSISTED on the exit (§5.3), so condition (1) holds by construction and condition (2) is a proved contract (§5.4), with the 8.3.0 history classified exact-vs-ambiguous rather than guessed (§5.7). Every claim is measured on the 8.3.0 tree.

### 5.1 API shape (revised — the helper receives the exit, not an amount)

- Two `@api` methods on `AdvanceInvoiceBuilder` (one helper, both exits, S4 settled):

```php
public function deductionLine(CreditMovement $exit): array       // APPLIED exit → frozen deduction line
public function rectificativeLines(CreditMovement $exit): array  // REFUNDED exit → frozen rectificative lines
```

- The G1 race is dissolved by construction, not narrowed: the round-1 shape `(entry, advance, amountApplied)` made the last-exit decision depend on WHEN the helper ran relative to `remaining()`; revision 2 keys everything off the COMMITTED exit row — the entry is `$exit->consumes`, the advance is the entry's `advance_invoice_id`, the take is `-$exit->amount` (the exit row's own amount, immutable), and the position comes from the band STORED on the exit row itself (§5.3). The helper is a pure read of that column: call timing is irrelevant, and a repeated call for the same exit returns the same band because it reads the same stored value.
- `deductionLine()` requires an APPLIED exit (`CreditMovementKind::APPLIED`, `allocation_id` present — the line lands on the invoice the exit's allocation paid): returns the item array for `createInvoice()`'s frozen path on the LATER invoice — signs inverted, `deducts_invoice_id = (string) $advance->id`, description naming the advance's fiscal number, `quantity: 100`.
- `rectificativeLines()` requires a REFUNDED exit: returns the frozen line list for a PARTIAL rectificative of the advance, issued through the existing `SettlementService::rectify()` — no new artifact type (S1 settled decision 4).
- **Validation of the received exit (fail-loud, zero writes):** not an exit → `InvalidCreditMovementException::notAnEntry`; reversed (`reversed_at` set — no artifact exists to compute for a reversed exit; its rectification duty applies only to an ALREADY-computed artifact, §5.4) → `InvalidCreditMovementException::reversed`; entry missing or not an entry → `InvalidAdvanceInvoiceException::notTheAdvanceEntry`; the entry's `advance_invoice_id` null or pointing at a non-rectifiable document → `InvalidAdvanceInvoiceException`.
- **`SettlementService::rectify()` gains one additive optional parameter** (kept from round 1, now with the G10 validation set): `rectify(Invoice $original, ?int $amount = null, ?string $settlementOperationKey = null, ?array $items = null)`. When `$items` is supplied, it is used verbatim as the frozen items (bypassing `clonedVerbatimItems()`/`differenceItems()`, `SettlementService.php:493`/`:523`) and `$amount` must be null — both supplied → new additive `InvalidRectificationAmountException::itemsWithAmount`. Validation of supplied items, before any write:
  - every item: `total_amount < 0` (rectificative lines are negative), and `taxable_amount + total_tax_amount === total_amount` (larabill's line identity);
  - every `taxes_applied` entry: `amount <= 0`, and `source_rate_id` + `rate` must MATCH an entry of the original's frozen breakdown — the rectificative corrects the same operation, and a rate the original never carried is an invented distribution (AID-589 doctrine, same reasoning as `UnresolvableRectificationRateException`, `SettlementService.php:541`);
  - per item, `Σ taxes_applied[].amount === total_tax_amount`; across items, `Σ total_amount < 0`; empty `$items` → loud;
  - **the exit-sum pin (H8):** the SUM of the items a consumer passes to rectify a REFUNDED exit must equal that exit's take exactly; the pin is enforced where the exit is known — `rectificativeLines()` guarantees `Σ |total_amount| === |$exit->amount|` over its own output and asserts it defensively (`InvalidAdvanceInvoiceException::itemsDoNotSumToExit`), because `rectify($items)` must stay exit-agnostic (its items may legitimately come from other futures); R26 pins the identity.
- All existing guards run unchanged (`assertRectifiable()`, `SettlementService.php:463`; the keyed adoption branch `:303` runs BEFORE any creation, as today); unkeyed, items-less calls are byte-for-byte identical to 8.3.0 (regression §8.4). The signature is `@api` surface — additive optional parameter, minor-safe.

### 5.2 The advance's frozen breakdown and the rounding function f

- The breakdown is read from the advance's lines' immutable `taxes_applied` snapshots — the same frozen source `differenceItems()` reads (`SettlementService.php:525-546`). **Snapshot validation (G6), before anything else:** the advance built by §4 carries exactly one rate or a tax-free line; the helper refuses anything else loud, with zero writes: two or more distinct `source_rate_id` → `InvalidAdvanceInvoiceException::multiRateTaxGroup`; an entry missing `source_rate_id`, or the same id repeated across lines → `::brokenAdvanceSnapshot`; `Σ taxes_applied[].amount !== line.total_tax_amount` on any line → `::brokenAdvanceSnapshot`. A hand-built multi-rate advance never gets a pro-rata — the attribution problem is refused, not solved.
- Operative case: one rate (or the tax-free pseudo-rate). `G` = the advance's gross (`total_amount`), `T` = its tax (`total_tax_amount`; `0` for tax-free). The rounding function: `f(c) = HalfUp(c · T / G)` on exact `BigDecimal` for `0 ≤ c < G`, and `f(G) = T` exactly — the AID-1527 §3-bis discipline, precedent `frozenRateTaxAmount()` (`SettlementService.php:590-598`). An exit covering ledger segment `[a, b)` of its entry gets `tax = f(b) − f(a)`, `base = (b − a) − tax`.

### 5.3 The band is PERSISTED on the exit (revision 3 — operator decision L8: «guardar la posición en la salida»)

- **The column.** `credit_movements.band_start`: `$table->bigInteger('band_start')->nullable()`, the base-100 CENT OFFSET at which the exit's band starts on its entry's tape. The band of an exit is `[band_start, band_start + abs(amount))` — the end is DERIVED by arithmetic, never stored. NULL on entries (they own the tape, they hold no band), on legacy rows the migration did not backfill (§5.7), and on exits of entries declared unresolvable (§5.7). The migration and its five-piece checklist are in §1; no index is added — band assignment reads the exits of ONE entry (existing `consumes_movement_id` index, `2026_10_24_000001_add_allocations_and_credit_movements.php:285`).
- **The helper only READS the stored band:** no replay, no clock reading, no `reversed_at` ordering. Revision 2's derivation (first-fit replay over rows, §5.3–§5.4 rev 2) and its two declared residuals — the same-second reversal tie-break (H1) and the COMB clock step-back (H2) — are RETIRED, not narrowed: there is nothing left to reconstruct, and the two OPEN findings of §11 die with the design they attacked.
- **The operator's premise, verified (L8: «cada `CreditMovement` de salida consume una sola entrada y lleva un importe», `CustomerCredit.php:474-498`):** every exit row carries exactly ONE `consumes_movement_id` (nullable FK, `2026_10_24_000001_add_allocations_and_credit_movements.php:258-263`) and ONE scalar `amount` (`:248`); both creators build one row per (entry, take) — `recordExit()` (`CustomerCredit.php:474-498`) and `consumeEntries()` (`PaymentService.php:513-551`). **Verdict: YES — one contiguous band per exit row ALWAYS suffices.** The band is a single interval of length `|amount|` by construction. The only way a take cannot sit in ONE contiguous free gap is handled at CREATION by splitting it into several exit rows, one per gap (§5.4) — and the row-level premise still holds for every resulting row: one entry, one amount, one contiguous band.
- **Census of exit writers (H3, measured on the 8.3.0 tree):** exits are created in exactly TWO places — `CustomerCredit::recordExit()` (`CustomerCredit.php:474-498`, called by `apply()` at `:228` for APPLIED and `refund()` at `:268` for REFUNDED) and `PaymentService::consumeEntries()` (`PaymentService.php:513-551`, APPLIED, called from `allocate()`). Every other `CreditMovement::query()->create` in `src/` creates an ENTRY, never an exit: the SURPLUS entry of `reverseAllocation()` (`PaymentService.php:448-465`) and `recordRemainder()` (`PaymentService.php:562-580`); `CreditMovementFactory` is test-only. Revision 2's «ONLY creator» claim is corrected here.
- **The band is assigned UNDER the EXISTING source-payment lock** — no new lock: `apply()`/`refund()` take `lockPayments()` as the FIRST statements of their transactions (`CustomerCredit.php:202`, `:263`, via `:373-394`), and `allocate()` takes the payment row X lock as the first statement of its transaction (`PaymentService.php:268-272`). Both exit creators therefore serialize on the source payment row of the entry they consume, so the assignment below is race-free by the lock larabill already holds to COMMIT.
- **Assignment algorithm (both creators, inside the locked transaction, before each INSERT):** read the entry's ACTIVE exits' stored bands; the free tape is `[0, G)` minus those bands (`G` = the entry's `amount`, immutable); fill the take LOWEST-GAP-FIRST; each filled run becomes ONE exit row with its `band_start` = the gap's start. A take larger than every single free gap is split per §5.4; a take exceeding the TOTAL free space (Σ gaps ≠ `remaining()` — broken ledger arithmetic) → `InvalidAdvanceInvoiceException::cannotPlaceExit`, loud, zero writes.

### 5.4 The reversal contract and the split rule (revision 3 — L8: «cómo se libera o reutiliza el tramo sin alterar el reparto de salidas vigentes ni dejar solapamientos»)

- **Where reversals happen (measured, carried from rev 2):** the ONLY writer of `reversed_at` on EXITS in 8.3.0 is `PaymentService::reverseAllocation()` (`src/Services/PaymentService.php:414`), which reverses ALL active APPLIED exits of ONE allocation atomically and only when they fully fund it (`:433-440`, `LogicException` otherwise), stamping them at `:441-447`. REFUNDED exits have NO reversal writer in 8.3.0 — a declared writer for 8.4 (S1 keeps the artifact vocabulary). The entry itself is payment-reversed only with zero active exits (`PaymentService.php:349-356`); `remaining()` grows automatically because it sums only non-reversed exits (`CreditMovement.php:135-146`).
- **The contract fixed:**
  1. **Freeing is a read-side fact, not a write.** A reversal stamps ONLY the audit columns — the reversed exit's stored band STAYS on the row (audit history). The free tape is computed from ACTIVE rows only (§5.3), so the band returns to the free tape with no write, no migration, and NO recomputation of any surviving exit's band.
  2. **Issued artifacts of live exits are NEVER recomputed.** The band is written once at creation (§5.3); the helper reads it (§5.1); a reversal never rewrites another row's band; every already-issued artifact keeps its frozen figures. The reversed exit's OWN artifact is fully rectified (net zero): an APPLIED exit's deduction line is dropped by the consumer if the later invoice is still a draft, or countered through `SettlementService::rectify()` on the document carrying the line if issued (no new artifact type, S1); a REFUNDED exit's rectificative likewise (declared for a writer 8.3.0 does not have).
  3. **Reuse is legal AFTER full rectification.** A freed band may be assigned to a NEW exit — because the reversed artifact is rectified to net zero, no two LIVE artifacts ever claim the same band range; what telescopes in the proof below is the tape of LIVE exits.
  4. **Non-overlap is an invariant of assignment, not a hope:** a band is only ever assigned into a free gap computed under the source-payment lock (§5.3), so active bands are pairwise disjoint by construction, in every intermediate state.
- **The split rule (when the take does not fit ONE free gap) — reachable, so it must be defined:** holes plus frontier can leave e.g. two free gaps of 600 and 400 cents for a take of 1000. Rule: the creator fills the gaps LOWEST-FIRST and inserts ONE EXIT ROW PER GAP, all consuming the same entry, all inside the same locked transaction, the last gap possibly partially filled; each row's `band_start` is its gap's start and its `|amount|` the length it fills.
  - **Compatible with `plan()`:** `plan()` (`CustomerCredit.php:405-451`) visits each entry at most once and returns ONE take per entry; the split happens AFTER the plan, at creation time, and Σ of the split rows equals the plan's take exactly — so the per-payment sums `apply()` accumulates (`CustomerCredit.php:220-232`) and the resulting allocation `applied_amount` are unchanged.
  - **Compatible with the `PaymentAllocation` funding check:** `reverseAllocation()` SUMS the active APPLIED exits of the allocation (`PaymentService.php:433-440`, `$exits->sum(...)` over `:430-434`), so N rows summing to `applied_amount` pass exactly as one row would, and they are reversed TOGETHER (they share the allocation). The «funded fully or not at all» invariant is untouched.
  - **Compatible with FIFO:** FIFO orders ENTRIES — `orderBy('occurred_at')->orderBy('id')` in `plan()` (`CustomerCredit.php:413-414`) and `consumeEntries()` (`PaymentService.php:522-527`); the number of exit ROWS per entry plays no role in any ordering. `remaining()` sums exits (`CreditMovement.php:135-146`) — row count irrelevant; `reverse()`'s zero-active-exits precondition (`PaymentService.php:349-356`) is an existence check — unaffected.
- **The split rule changes `refund()`'s documented contract (J5):** the 8.3.0 docblock promises «one REFUNDED exit per entry consumed FIFO» (`CustomerCredit.php:242-244`); after this change ONE consumed entry may carry SEVERAL REFUNDED rows — one per filled gap — and `refund()` returns all of them in its collection. The docblock is updated in T7 and the CHANGELOG `Changed` entry declares it (§7). `apply()`'s return shape does not change — it returns allocations, not exits — so the documented consumer path to EVERY APPLIED exit row of an `apply()` is by `allocation_id`: all rows of a split share the SAME `allocation_id` (rule above), and the `CreditMovement` rows filtered by that `allocation_id` + APPLIED kind (or, per entry, by `consumes_movement_id` + kind) return every row of the split.
- **Worked example — reversal in the middle + refill** (`G = 10000`, `T = 1736`, i.e. an advance of 100,00 € @21 %; `f` per §5.2):

  ```text
  exit1 take 1000 -> band [0,1000)      tax f(1000)-f(0)   = 174   base 826
  exit2 take 1000 -> band [1000,2000)   tax f(2000)-f(1000)= 173   base 827
  exit3 take 8000 -> band [2000,10000)  tax f(G)-f(2000)   = 1389  base 6611   (entry exhausted:
                                        174+173+1389 = 1736 = T; 826+827+6611 = 8264 = G-T)
  reverse exit2 (reverseAllocation on an allocation whose only active APPLIED exit is
                 exit2); its artifact is fully rectified; band [1000,2000) returns to the
                 free tape automatically — the stored band stays on the row for audit.
  exit4 take  700 -> lowest free gap [1000,1700)   tax f(1700)-f(1000)=295-174=121  base 579
  exit5 take  300 -> gap [1700,2000) filled exactly tax f(2000)-f(1700)=347-295= 52  base 248
                   (exhausted again: [0,1000)+[1000,1700)+[1700,2000)+[2000,10000) tile [0,G);
                    live Σ tax 174+121+52+1389 = 1736 = T; live Σ base 8264 = G-T)
  ```

- **Worked split example:** exits 1000 (`[0,1000)`, tax 174) and 1000 (`[1000,2000)`, tax 173); reverse the FIRST; then a take of 1500 — free tape is the hole `[0,1000)` plus the frontier beyond `[1000,2000)`; one row cannot hold 1500 contiguous → the creator inserts TWO rows: band `[0,1000)`, amount `-1000`, tax 174, base 826; band `[2000,2500)`, amount `-500`, tax `f(2500)-f(2000) = 434-347 = 87`, base 413. Same `consumes_movement_id`; if APPLIED, same `allocation_id` and the funding check sees `-1500 = applied_amount` ✓; FIFO and `remaining()` unaffected.
- **Proof (non-overlap, tiling, telescoping).** Active bands are pairwise disjoint (invariant 4) cent-aligned sub-intervals of `[0, G)` — cent-aligned because every amount is a base-100 integer and every `band_start` is 0 or a previous band's end. At exhaustion (`remaining() = 0`) the ACTIVE takes sum to `G`, so the active bands' total length is `G`, and disjoint cent-aligned sub-intervals of `[0, G)` with total length `G` TILE `[0, G)` exactly; ordered by position they are contiguous, so `Σ (f(b_i) − f(a_i))` telescopes to `f(G) − f(0) = T`. Per rate: the same argument on the single rate's tape (multi-rate refused, §5.2). Intermediate states: `Σ active gross = G − remaining()` exactly; every exit's split sums to its own gross (`b − a = |amount|`, split rows included); a still-open hole carries at most a rounding residue that closes when the hole is refilled — no live artifact is ever touched retroactively.
- **The round-2 first-fit counterexample survives as the justification for lowest-gap-first refill (pinned as R20):** frontier-continuation prices `[1000,2000)` twice and loses the hole (Σ live tax 1735 ≠ 1736); first-fit refills it and lands on `T` exactly.

### 5.5 Where the read happens — the existing lock order, restated for the exit-based shape

- The ledger exits are created ONLY under the source-payment locks, in exactly TWO places (census, §5.3): `CustomerCredit::apply()`/`refund()` via `recordExit()` (`OutermostTransaction::assert()` first, `CustomerCredit.php:189`, `:256`; `lockPayments()` as the FIRST statements, `:202`, `:263`, via `:373-394`; the FIFO plan, `:405-451`; `recordExit()`, `:228`, `:268` via `:474-498`) and `PaymentService::allocate()` via `consumeEntries()` (payment row X lock as the first statement, `PaymentService.php:268-272`; `consumeEntries()` at `:513-551`). The helper adds no new lock and needs none: it reads the STORED band of the received exit (§5.3), never the ledger state.
- **Contract on the caller (weakened from round 1, honestly):** the consumer invokes the helper in the same unit of work as the exit-creating `apply()`/`refund()`/`allocate()` it documents, immediately after it — but the pro-rata no longer DEPENDS on that timing (§5.1): the band is already persisted on the exit row (§5.3), so the round-1 G1/G2 races AND the round-2 reconstruction residuals (H1 same-second tie-break, H2 COMB step-back) are dissolved, not narrowed. A late or retried computation reads the same stored column.
- Edge cases pinned by tests (§8.3): single full deduction; partial-then-last cent absorption; previous exits from both artifact kinds; mixed APPLIED + REFUNDED on one entry; tax-free advance (`T = 0`: every tax is 0, every base equals its band's length — the tiling invariant is carried by the base alone); a FULL rectificative of the advance counts as a previous exit; reversal + re-consumption (the §5.4 counterexample); two exits committed before either artifact (G14); a take split across gaps into several exit rows (R28); an unresolvable legacy entry refusing loud (R29).

### 5.6 The link is one-to-one in BOTH directions (O2 — operator decision L7: «Sí, en el enlace»)

- Measured gap: `linkAdvanceInvoice()` (`CreditMovement.php:189-208`) guards one direction only — an entry cannot link twice, but two entries CAN link one advance once each (round-1 G9 verified against `:171-208`).
- **Fix, no schema change (H6 resolved concretely — exact builder, `ERROR 1093` unreachable).** `linkAdvanceInvoice()` becomes, inside a short transaction (plain `DB::transaction`), in this order — **caller contract (K1, round 4): call it as the OUTERMOST transaction, or inside a wrapper that has made NO prior read**, the same snapshot rule `PaymentService` documents for `receive()`/`allocate()` (`PaymentService.php:88-101`): under REPEATABLE READ a plain read made earlier by the caller fixes the snapshot, and the conflict query of step (3) would read stale rows even after the invoice lock is acquired. Not enforced with `OutermostTransaction::assert()`, on purpose: 8.3.0's `linkAdvanceInvoice()` has no transaction requirement and adding a new refusal would break existing callers; a locking read of the conflict set was rejected because an empty-range locking read on `advance_invoice_id` is a gap lock, the AID-715 deadlock pattern. Steps: (1) FIRST statement, the locking read of the advance invoice row — `Invoice::query()->whereKey($advance->getKey())->lockForUpdate()->firstOrFail()` — the serialization point; (2) on the LOCKED instance, the document checks (next bullets — document KIND first, then DRAFT status); (3) the advance-side conflict set materialized in PHP AFTER the lock: `CreditMovement::query()->select('id')->where('advance_invoice_id', $advance->getKey())->where('id', '!=', $this->getKey())->pluck('id')`; (4) **if the conflict set is NON-EMPTY → `CreditMovementAlreadyLinkedException::forAdvance(...)` is thrown IMMEDIATELY and NO UPDATE is issued** (J1, round 3 — the round-3 table's verdict: revision 3's `whereNotIn('id', $banned)` excluded the winner and let the loser link anyway): the winning entry id comes from the set itself, and the loser's own row is never written — it stays NULL; (5) the conditional UPDATE keeps ONLY the entry-side guard: `whereKey($this)->whereNull('advance_invoice_id')->whereIn('kind', entryKindValues())` — still needed because two advances racing to link the SAME entry serialize on DIFFERENT invoice locks, so one of them can pass its own conflict check and must lose on the entry's `whereNull` guard, surfacing `::forMovement` from the `affected === 0` handling (unchanged from 8.3.0). **Why `ERROR 1093` cannot arise (restated, now trivially):** the conflict ids are consumed as a PHP emptiness check only — the UPDATE contains no subquery and not even a `whereNotIn` over `credit_movements`, so the statement cannot reference its own target table beyond the row it updates; MySQL's same-target-table refusal never arises, and the SQL is byte-identical on MySQL 8.4 and MariaDB 11.4. The materialization is race-free precisely because it happens AFTER the invoice X lock: two concurrent linkers of the same advance serialize on that lock, the loser's materializing read sees the committed winner, its conflict set is non-empty, and it throws BEFORE any UPDATE — the loser's row stays NULL (J1).
- **Document-kind check (J7):** on the same locked instance, the advance must be a fiscal INVOICE — `$advance->type !== 'invoice'` → new additive named constructor `InvalidAdvanceInvoiceException::advanceNotAnInvoice(string $invoiceId)`. The check exists because a proforma advance (`type = 'proforma'`, `Invoice.php:83`) carries `invoice_document_status = NULL` (`Invoice.php:62`), so the DRAFT check alone would refuse it without naming the real cause; ordering is kind first, then DRAFT.
- **Draft check at link time (L9):** while the advance row is X-locked, its `invoice_document_status` must be DRAFT — a non-draft advance (issued, converting, cancelled) → new additive named constructor `InvalidAdvanceInvoiceException::advanceNotDraft(string $invoiceId)`. The X lock makes the check race-free: a concurrent `issue()` of the same advance serializes on the same row lock.
- **Lock order and the documented deadlock (H10):** the linker takes the invoice row BEFORE touching `credit_movements`. The cycle with a concurrent `CustomerCredit::apply()` to the same advance invoice — which holds its payments, takes the invoice X lock, and takes FK shared locks on entry rows while inserting exits — REMAINS POSSIBLE; the model docblock already declares it as SQLSTATE 40001 / error 1213 with the consumer-retry contract (`CreditMovement.php:178-184`), and the new order does not remove the cycle: it documents it on the new order and now TESTS it (R27) — one side wins, the loser may take a 40001, and its retry succeeds. The docblock note is updated, not weakened.
- **Refusals:** entry already linked (to any advance) → existing `CreditMovementAlreadyLinkedException::forMovement`; advance already linked to another entry → new additive named constructor `::forAdvance(string $advanceInvoiceId, string $winningEntryId)` — thrown at step (4) from the materialized conflict set, which names the winning entry; the loser's own link is still null, so `forMovement` cannot name the blocker; advance not a fiscal invoice (proforma) → `::advanceNotAnInvoice` (J7); advance not a draft → `InvalidAdvanceInvoiceException::advanceNotDraft`. Re-linking the same pair stays a refusal (the link happens once; no stable no-op is added).
- **The documented consumer sequence is build → link → issue (L9) — and what larabill does and does NOT enforce:** larabill guarantees the LINK exclusivity (one entry ↔ one advance, both directions, atomic — this section) and that the advance was a DRAFT at link time. It does NOT, and in 8.4 will not, prevent `InvoiceService::issue()` on an unlinked advance draft: `issue()` is a generic `@api` primitive with no hook into the credit ledger, so «only the linked one can be issued» is the CONSUMER's documented contract (clientes retries the same linked draft after an issuance failure and never builds another for the entry), NOT a code guarantee — stated here so the spec never claims a guarantee the code does not give. A stray issuance of the orphan draft produces a valid, unlinked invoice: no corruption of the advance or the ledger, but a wrong artifact whose cleanup is the consumer's (same O5 responsibility). The sequence test R25 pins the package-side guarantees and documents the orphan's raw issuability.
- O5 interplay (L7) + L9: duplicate DRAFTS remain possible (§4.2) — the link boundary is what stops the second draft from ever being LINKED, and the consumer contract is what keeps it from being ISSUED as an advance of the same entry. The tests pin both results (§8.2 R10b, §8.3 R24, R25).

### 5.7 The 8.3.0 upgrade contract (L8: backfill exact or refuse — never heuristic-as-fact)

- The migration (`add_band_start_to_credit_movements`, ONE file: `addColumn` DDL followed by the data programme — the migration is NOT transactional on MySQL/MariaDB, so the boundaries are defined in the last bullet) classifies every entry holding 8.3.0-era exits and either backfills its bands or declares the entry unresolvable. L8, verbatim: «No se debe presentar un backfill heurístico como dato histórico cierto.» Scale stated honestly: 8.3.0 shipped 2026-10-25, so real legacy exits may be few — the contract does not RELY on that; it must be correct for any volume.
- **EXACT (backfill) — an entry E qualifies iff ALL hold, each computed from stored data only:** **(operator L12) Wording:** E1+E2+E3 is a CONSERVATIVE RECONSTRUCTION CRITERION, not a proof of the real historical order; CHANGELOG and docs describe it so.
  - **(E1) no reversed exits:** no row with `consumes_movement_id = E.id` carries `reversed_at` (a stored column, `2026_10_24_000001_add_allocations_and_credit_movements.php:277`). Without a reversal the tape was never disturbed: no hole was ever opened, no re-consumption order exists to reconstruct, and the only freedom left is the creation order.
  - **(E2) provable creation order:** E's active exits, ordered by `id`, are also in STRICTLY INCREASING `created_at` (`:282` `timestamps()`) — a tie is as disqualifying as a decrease (J2, round 3; revision 3's «non-decreasing» is retired). Why a tie cannot be resolved from stored data: `created_at` is second-precision and is the ONLY order evidence stored independently of the `id`; when two exits share the same second, the COMB `id` order is the sole remaining candidate — but that is exactly the evidence under test (the H2 clock step-back can displace the COMB's timestamp by one step), so with a tie there is no third witness: an arbitrary exit has no artifact (E3 is vacuous without one — the same reason J2 was raised), and the source-payment lock serializes the commits but stamps nothing. Choosing between two orders with equal stored evidence would be precisely the heuristic-as-history L8 forbids. With strict increase the two evidences AGREE, and first-fit stacking from 0 in that order is the UNIQUE band assignment consistent with both stamps and E1.
  - **(E3) artifact cross-check where an artifact exists:** if E is linked to an advance, every exit of E whose fiscal artifact exists must recompute exactly against the proposed bands (`f(b) − f(a)` equals the artifact's frozen per-rate tax, §5.2). A mismatch reclassifies E AMBIGUOUS — a stamp that lied is caught wherever an artifact witnesses the truth.
- **AMBIGUOUS (leave NULL, refuse loud) — any of:** a reversed exit on E (the hole/refill order is not in the data); E2 fails (`created_at` ties or decreases along `id` order, J2); E3 fails. ALL of E's exits keep `band_start` NULL — including its reversed rows, which the tape never reads. The unresolvability needs NO extra marker column: after 8.4 an ACTIVE exit with `band_start` NULL cannot be born (every creator writes a band, or propagates NULL on an unresolvable entry — next bullet), so «an active exit with NULL `band_start`» IS the declaration, checked by the helper before anything else.
- **New exits on an unresolvable entry:** the creators detect an active NULL-band exit on the target entry and write `band_start = NULL` on the new exit too — no guess, no quiet re-anchor. The LEDGER keeps working untouched (bands are fiscal metadata; `remaining()`, `plan()`, FIFO and the funding checks never read `band_start`); the whole entry stays unresolvable, and the helper refuses it loudly with `InvalidAdvanceInvoiceException::unresolvedEntryPosition(string $entryId)` — never a split invented from an ambiguous history. Resolving a declared-unresolvable entry (an operator decision over real evidence) is out of 8.4 scope and documented as such.
- **How the migration PROVES it:** one pass over active exits grouped by `consumes_movement_id` — per entry evaluate E1–E3 (E3 against the linked advance's frozen breakdown), compute the first-fit stack for EXACT entries and write the `band_start` values; AMBIGUOUS entries are skipped (stay NULL). **The DDL/backfill boundaries (J4 — revision 3's «inside the migration's own transaction» is RETIRED as false on the target engines):** on MySQL 8.4 and MariaDB 11.4 a migration runs wrapped in a transaction only when the grammar declares schema-transaction support (`vendor/laravel/framework/src/Illuminate/Database/Schema/Grammars/Grammar.php:551-554`), and those grammars ship `$transactions = false` (`Grammar.php:31`), so `vendor/laravel/framework/src/Illuminate/Database/Migrations/Migrator.php:448-451` runs the callback BARE — a mid-migration stop is a real state, not an abstract one. The boundaries are then: (1) the `addColumn` DDL runs FIRST — a stop after it leaves the column present with every row NULL, i.e. the unprocessed state; (2) the backfill runs PER ENTRY, each entry's classification + writes inside its OWN `DB::transaction` — a partial stop leaves a prefix of entries banded and the rest untouched; (3) a RE-RUN after a partial stop is correct and required: NULL bands on active exits mean «not yet processed or declared ambiguous» (the declaration reading above is unchanged), the already-banded entries classify EXACT again and their writes are no-ops. The migration is therefore IDEMPOTENT and RESUMABLE after a partial stop, and the predicate is pure SQL/PHP over stored columns — nothing clock- or environment-dependent.
- **Upgrade-path test (AID-398 pattern, `tests/Integration/UpgradePath/`, both engines — R30/R31/R33):** migrate the v8.3.0 base set (the manifest's `in_base` rows), seed legacy state, run the migration, verify: an exact entry (E1+E2, advance linked with matching artifacts) receives the expected bands; an entry with one reversed exit keeps NULL everywhere and its helper call refuses; an entry whose `created_at` contradicts `id` order keeps NULL; a linked entry whose artifact disagrees with the computed band keeps NULL (E3 in action); an interrupted backfill resumed to completion (R33, J4).
